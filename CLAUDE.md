## Knowledge Graphs

This project has TWO knowledge graph systems. **graphify** is fully operational with rich structure. **Understand Anything** is installed and ready but needs an AI agent pipeline to generate edges, layers, and tours.

### graphify (Active — use for queries)

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships (1,284 nodes, 2,453 edges, 99 communities).

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

### Understand Anything (Installed — file-level graph only)

Location: `understand-anything-plugin/` and `.understand-anything/knowledge-graph.json`

Status: Plugin installed, core package built, project scanned (520 files, 509 nodes in graph). The graph contains file nodes only (no edges yet) — the full multi-agent pipeline (edges, layers, guided tours) requires running `/understand` in a compatible AI agent (Claude Code, Cursor, Codex, etc.) or using the scripts directly.

Key files:
- `understand-anything-plugin/` — Full plugin source (packages/, skills/, agents/)
- `.understand-anything/knowledge-graph.json` — Basic file-level graph (regenerate: `node skills/understand/scan-project.mjs <root> <out>` → build via GraphBuilder)
- `.understandignore` — Exclusion patterns for scanning
- For the interactive dashboard, build `packages/dashboard/` and run it

To get the full value (import relationships, architectural layers, guided tours, domain analysis):
- Run `/understand` in a compatible AI agent (Claude Code, Codex, etc.)
- Or `node skills/understand/scan-project.mjs /root/my-project /tmp/scan.json` for re-scan

## Client Onboarding — Brand Profile Requirement

When a new client is added to the system (via API, seed data, or manual creation), you MUST create their brand profile documentation before doing any content work for them.

Process:
1. Create `doc/clients/{slug}/` directory
2. Use `doc/clients/_template.md` as starting point
3. Research and populate all sections:
   - Scrape the client's website for brand info, colors, fonts, logos
   - Research company on LinkedIn, social media, business directories
   - Extract CSS color palette and typography from site assets
   - Document all tech stack components
   - Record all known contacts, emails, phones, admin access
   - Define SEO content pillars and keyword strategy
4. Save files:
   - `brand-profile.md` — full brand intelligence
   - `technical-reference.md` — integration details  
   - `seo-content-guide.md` — content strategy
   - `contacts.md` — people and access
5. Commit and push to GitHub

Existing clients are already profiled at `doc/clients/`. Read the relevant profile before doing any work for that client.

## Article Content Standard

Every article generated by the plugin or written in this project must follow the **EEAT Content Framework** (`doc/EEAT-content-framework.md`). The framework mandates:

- 100% original writing — no copying, paraphrasing, or rewriting competitors
- Writing from first principles with original structure, examples, and insights
- Deep EEAT: Experience, Expertise, Authoritativeness, Trustworthiness
- Semantic SEO for topical authority — not keyword density
- Self-review pipeline before output (14 quality steps)
- Never fabricate statistics, studies, quotes, or sources
- Evergreen content that ranks for years without major rewrites
- Human writing — no AI clichés, filler, robotic patterns, or generic conclusions
- Every paragraph must provide unique value; delete anything that doesn't

The full framework is at `doc/EEAT-content-framework.md`. Read it before writing any article.

## DevOps Pipeline (Zero-Error Deployment)

### Pipeline Flow
```
CI (on PR/push) → Staging (auto on main) → Canary (20%) → Production (manual approval)
```

### Workflows
| Workflow | File | Trigger |
|----------|------|---------|
| CI | `.github/workflows/ci.yml` | PR/push to main |
| Staging | `.github/workflows/deploy-staging.yml` | Push to main |
| Production | `.github/workflows/deploy-production.yml` | Manual dispatch |
| Legacy Build | `.github/workflows/docker-deploy.yml` | Push + tags |

### Deploy Commands
```bash
# Smoke test (run locally after deploy)
./scripts/smoke-test.sh

# Rollback to previous version
./scripts/rollback.sh

# Rollback + restore DB
./scripts/rollback.sh --restore-db /tmp/pre-deploy-20260708-120000.dump
```

### Required GitHub Secrets
| Secret | Used By | Description |
|--------|---------|-------------|
| `STAGING_HOST` | staging workflow | Staging server IP/hostname |
| `STAGING_USER` | staging workflow | SSH user |
| `STAGING_SSH_KEY` | staging workflow | SSH private key |
| `STAGING_DOMAIN` | production validation | Staging URL for pre-deploy check |
| `DEPLOY_HOST` | production workflow | Production server IP/hostname |
| `DEPLOY_USER` | production workflow | SSH user |
| `DEPLOY_SSH_KEY` | production workflow | SSH private key |
| `SLACK_WEBHOOK_CI` | CI workflow | Slack webhook for CI failures |
| `SLACK_WEBHOOK_DEPLOYS` | staging+prod | Slack webhook for deploy events |
| `OPENAI_API_KEY` | production env | OpenAI API key |
| `JWT_SECRET` | production env | JWT signing secret |

### Quality Gates (in order)
1. ✅ TypeScript type check (`tsc --noEmit`)
2. ✅ ESLint (no warnings)
3. ✅ Unit + service tests (`vitest`)
4. ✅ DB migration dry-run (all `migration_*.sql` applied)
5. ✅ Security audit (npm audit + secrets scan)
6. ✅ Build check (`npm run build`)
7. ✅ Staging healthy (pre-deploy check)
8. ✅ Canary health check (15 attempts, 2s interval)
9. ✅ Canary observation window (120s)
10. ✅ Full rollout + smoke tests (health, API, frontend, DB, Redis)
11. ✅ Auto-rollback on any failure

### Rollback Triggers
- Health check failure → auto-rollback to `prev-production` image
- Smoke test failure → auto-rollback + Slack notification
- Manual rollback via `./scripts/rollback.sh`
- DB restore available from pre-deploy backups at `/tmp/pre-deploy-*.dump`

### Monitoring
- Health endpoint: `GET /health` (returns DB, Redis, OpenAI, and service status)
- Prometheus metrics: `GET /metrics`
- Docker container healthchecks built into all services
- Heartbeat email alerts via Gmail SMTP (configured in `.env`)
